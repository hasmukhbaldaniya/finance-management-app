# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in `desktop/`.

## Overview

`desktop/` is the Electron + Rust desktop counterpart to `frontend/` — the eighth independent app in
this monorepo, with its own `package.json`/lockfile, installed and run separately (`npm install` /
`npm run dev` from inside `desktop/`, never from the repo root). It logs into the same
`gateway-service` `frontend/` does and is, screen-for-screen, a full port of it: auth (Login, Forgot
Password, Register, Onboarding), Dashboard/Reports, all of Company Settings (Grades, Departments,
Roles & Privileges, Associated Organizations, Employees, Categories), Trips, Claims, and Profile/Help
— plus the `ComingSoon` stubs for Approvals/Finance, since those are still stubs in `frontend/` itself
too. A Rust crate (`native/`) does local, genuinely CPU-bound work (receipt-folder duplicate
detection via content hashing) that would be the wrong tool for Node — `ai-service/`'s own Python
choice already established that a non-Node toolchain in one of these apps isn't a new kind of
exception.

**Toolchain note:** this app is pinned to Node `22.19.0` via `.nvmrc` — Electron 44 requires
`>=22.12.0`, above your machine's plain default (`22.11.0`). Run `nvm use` in `desktop/` before any
`npm`/`dev`/`build` command. TypeScript is pinned to `5.9.3`, matching `frontend/`'s own major
version — TypeScript 7 (a new, differently-implemented compiler) resolves some of MUI's more complex
generic typing (its polymorphic `component` prop) differently, and this app copies a large amount of
`frontend/`'s own MUI-based code verbatim, so staying on the same major version 7 avoids a whole class
of type errors that have nothing to do with actual behavior differences.

## Common Commands

```
nvm use                       # pin to Node 22.19.0 — do this first, every session
npm install                   # also runs build:native via postinstall
npm run dev                   # electron-vite dev — hot-reloads the renderer, rebuilds main/preload on change
npm run build                 # electron-vite build (out/) — no packaging
npm run build:native          # rebuild native/*.node after any Rust change (native/src/**)
npm run build:mac             # electron-vite build + electron-builder --mac --arm64 → dist/*.dmg, *.zip
npm run typecheck             # tsc -b --noEmit across all three targets
```

There is no lint/test runner configured yet (matches this being the newest app in the monorepo, with
no equivalent of `frontend/`'s Storybook/Cypress setup built out).

## Porting convention: how code moves from `frontend/` to here

Every screen and component here is a **port of the matching file in `frontend/`**, not a rewrite.
When you need to touch a screen, find its `frontend/src/app/**/page.tsx` (or
`frontend/src/components/**`) equivalent first — the desktop version should stay behaviorally
identical except for the two mechanical swaps below.

- **`next/link`'s `Link` → `react-router`'s `Link`**: `href=` becomes `to=`. The
  `component={Link}` MUI composition pattern (`<Button component={Link} to={...}>`,
  `<MuiLink component={Link} to={...}>`) is unchanged.
- **`next/navigation`'s `useRouter`/`useParams`/`useSearchParams` → `react-router`'s same-named
  hooks**: `useParams`'s shape is identical. `useSearchParams` differs — react-router's returns a
  `[URLSearchParams, setSearchParams]` tuple, so only the destructuring changes
  (`const [searchParams] = useSearchParams()`), not the `.get()` calls themselves. `router.push(x)`
  becomes `navigate(x)`; `router.replace(x)` becomes `navigate(x, { replace: true })`.
- **Any `<Suspense>` wrapper that exists solely because Next requires `useSearchParams()` to be
  Suspense-wrapped gets dropped** — react-router's `useSearchParams` has no such requirement, so the
  two-component split (an outer `Suspense` wrapper + inner page component) collapses to one.

Everything else — validation, API calls, MUI markup, business logic, comments explaining *why* — is
copied unchanged. If you're rewriting logic instead of doing one of the three swaps above, stop and
check whether `frontend/`'s version already does what you're about to write.

**Two known one-off deviations from pure verbatim porting**, both narrow and commented in place:

1. `components/ui/button.tsx`'s `ButtonProps` type has one added field: `to?: string`. MUI's real
   `ButtonProps` already types `href` (Button can render as an anchor natively), but has no way to
   know about react-router's own `to` prop name — this is a type-level fix for the router swap
   above, not a behavior change.
2. `native.ts`'s addon path resolves via `.replace("app.asar", "app.asar.unpacked")` — see
   "Packaging" below.

## The gateway bridge — why API calls happen in main, not the renderer

`gateway-service/src/app.ts` runs `cors({ origin: env.corsOrigin, credentials: true })` where
`corsOrigin` is a **single literal string** (`http://localhost:3000` by default), and every request
needs `credentials: "include"` since auth is entirely cookie-based (two httpOnly cookies set by
`auth-service` at login). A renderer's origin — `http://localhost:5173` in dev, `null` from a
packaged `file://` page — can never satisfy that single-string check, and credentialed CORS can't use
a wildcard. **Main-process requests aren't subject to CORS at all**, so every gateway call happens in
main instead — this required zero changes to `gateway-service` itself.

Concretely: `src/main/api/gateway.ts` holds a persistent session partition
(`session.fromPartition("persist:finance")`) and calls that session's own `.fetch()` — not `net.fetch()`,
which always uses Electron's *default* session and would never see this partition's cookies, and not
Node's global `fetch` (undici), which doesn't touch Electron's cookie store at all. Cookies persist
across restarts for free, and macOS encrypts Chromium's cookie store via Keychain.

**Three generic IPC channels are the entire surface for every one of the ~100 ported
`apis/**/*.api.ts` files** — never one channel per endpoint:

- `gateway:request` — plain JSON, behind `apiManager.ts`'s `apiCall`/`postJson`.
- `gateway:upload` — multipart. The renderer converts a `FormData`'s `File` entries into
  `{ fileName, mimeType, data: ArrayBuffer }` (File/FormData can't cross the IPC structured-clone
  boundary), and `gateway.ts` rebuilds a real `FormData` from those bytes on the main-process side.
- `gateway:download` — binary. Returns `{ data: ArrayBuffer, contentType }`; the renderer wraps it
  back into a `Blob`.

`apiManager.ts`'s exported names and signatures (`ApiError`, `GENERIC_ERROR_MESSAGE`, `apiCall`,
`postJson`, `uploadFile`, `downloadFile`) are unchanged from `frontend/`'s — every ported
`apis/**/*.api.ts` file calls them exactly the same way it always did and has no idea an IPC hop
exists underneath. `API_BASE_URL` is read from `VITE_API_BASE_URL` (`.env`, defaulting to
`http://localhost:4400/api`) — electron-vite injects any `VITE_`-prefixed env var into **all three**
build targets, including main, not just the renderer, so `src/main/api/gateway.ts` reads the same
variable name directly.

**If you add a new ported endpoint, you never touch the IPC layer** — just add the `.api.ts` file
under `apis/`, matching `frontend/`'s file, and it goes through the existing three channels
automatically.

## Conventions

Global rules in `~/.claude/CLAUDE.md` apply, with these desktop-specific decisions on top:

- **Styling: MUI** (`sx` prop + `styled` API), matching `frontend/` — not the CSS Modules used in
  this app's very first Phase 2/3 scaffold (retired once the real app shell was built in Phase 5).
  The entire `components/ui/*` primitive layer and every feature component are MUI-based ports;
  introducing a second styling system here would be exactly the "mixed styling systems" mistake the
  global CSS/Styling rule warns about.
- **Routing: `react-router` (the modern unified package, not the legacy split `react-router-dom`),
  with `HashRouter`** — not `BrowserRouter`. A packaged app loads over `file://`, which has no
  server to resolve a deep sub-path on reload; `HashRouter` keeps the whole route in the URL
  fragment, which a `file://` load already satisfies unconditionally.
- **State management: no data-fetching library** — `frontend/` has no React Query either
  (`frontend/CLAUDE.md` is explicit about this), so every ported screen keeps its original plain
  `useState`/`useEffect` fetch-on-mount pattern. This is a port, not a redesign.
- **Security**: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` on every
  `BrowserWindow`, set once in `src/main/index.ts` and never relaxed. The renderer's only surface is
  `contextBridge`'s narrow, hand-typed object in `src/preload/index.ts` — never expose `ipcRenderer`
  itself or a channel name the renderer can choose at runtime. `src/renderer/index.html` carries a
  CSP (`script-src 'self'`). No token, cookie, or credential ever reaches the renderer's JS context —
  verify this in DevTools after any auth-adjacent change (`document.cookie` should be empty;
  `window.api` should expose no token getter).
- **The Rust addon is main-process-only.** The renderer never imports `native/` directly; every
  native call goes through `src/main/ipc/native.ipc.ts`'s explicit channels. `src/main/native.ts` is
  the single `require()` site — everything else imports the addon from there.

## Rust addon (`native/`)

Built with `@napi-rs/cli` (Node-API / N-API — a stable ABI, so the same compiled `.node` loads in
plain Node and in Electron without a rebuild, and survives Electron version upgrades). `napi build`
generates `index.js`/`index.d.ts` from the Rust signatures — typed automatically, never hand-edited.

Current surface: `ping(name)` (the Phase 3 proof-of-life call) and `scanFolder(root)` (BLAKE3
content-hash duplicate detection over a folder — the real job Phase 4 gave it, ahead of Claim
Management's own invoice-file handling). Add new native functions to `native/src/lib.rs`, run
`npm run build:native`, then wire a channel in `src/main/ipc/native.ipc.ts` — same pattern both
existing functions already follow.

`npm run build:native` only ever builds for the host you run it on — locally that means
`darwin-arm64` on this machine. `native/package.json`'s `napi.targets` array lists every target this
app ships (`x86_64`/`aarch64` × `apple-darwin`/`pc-windows-msvc`/`unknown-linux-gnu`), but that array
only documents intent — it doesn't make `napi build --platform` cross-compile. Every non-host target
is built by `.github/workflows/desktop-release.yml`'s CI matrix, one job per OS+arch, each running
natively on its own runner (including GitHub's hosted `windows-11-arm` and `ubuntu-24.04-arm`
runners for the arm64 Windows/Linux jobs) — never cross-compiled from a single machine. See
"Packaging" below.

## Packaging

**Built for macOS, Windows, and Linux — always natively, never cross-compiled.** The Rust native
addon is a compiled binary tied to one OS+CPU architecture, so `.github/workflows/desktop-release.yml`
builds every target on its own real OS+arch runner and nowhere else: `macos-latest` (arm64),
`windows-latest` (x64) + `windows-11-arm` (arm64), `ubuntu-latest` (x64) + `ubuntu-24.04-arm` (arm64).
This is the CI matrix referenced in earlier versions of this doc as the right way to add non-macOS
targets — cross-compiling the addon with `cargo-xwin`/`cargo-zigbuild` was considered and rejected,
since a binary produced that way can't be launched or verified from the machine that built it.

Locally, each `npm run build:mac` / `build:win` / `build:linux` only ever produces a package for the
OS you're actually running it on — running `build:win` on this Mac will fail (no Windows toolchain,
no `aarch64`/`x86_64-pc-windows-msvc` Rust target installed), by design. Windows and Linux packages
only come from CI.

- `npm run build:mac` → `electron-vite build && electron-builder --mac --arm64` → `dist/*.dmg`, `dist/*.zip`.
- `npm run build:win` → `electron-builder --win` → `dist/*.exe` (NSIS installer). CI passes
  `--x64`/`--arm64` explicitly per matrix job so each Windows runner only builds the arch it can
  actually run natively — see `electron-builder.yml`'s `win.target.arch: [x64, arm64]`.
- `npm run build:linux` → `electron-builder --linux` → `dist/*.AppImage`, `dist/*.deb`. Same
  per-job `--x64`/`--arm64` split as Windows.

**A real dependency bug hit while wiring this up**: `electron-builder@26.15.3`'s bundled
`app-builder-lib` depended on `@noble/hashes@^2.2.0`, but `@noble/hashes` 2.x is pure ESM
(`"type": "module"`) while `app-builder-lib`'s blockmap step still does a plain CommonJS
`require("@noble/hashes/blake2.js")` — every `zip`/blockmap-producing build (which includes the
existing macOS `zip` target, so this wasn't new to Windows/Linux) failed with `ERR_REQUIRE_ESM`.
Confirmed via the registry that this was already fixed upstream: `app-builder-lib`'s `v26` dist-tag
(`26.16.1`) reverted to `@noble/hashes: ^1.8.0`, whose `1.8.0`+ releases ship a dual
`{"require": "./blake2.js", "import": "./esm/blake2.js"}` export the older 1.x line didn't have.
Fixed by bumping `electron-builder` to `^26.16.1` — no `overrides` field needed once the real
version-compatible range is pulled in directly.

**The one packaging-specific bug this app already hit and fixed**: `native.ts` resolves the addon's
path via `__dirname`, but inside a packaged app, `__dirname` still reports a path *into* `app.asar`
(the archive) even though `electron-builder.yml`'s `asarUnpack: ["native/**/*"]` means the addon's
real files only exist in the `app.asar.unpacked` sibling directory — a `.node` file can't be
`dlopen()`'d from inside the archive at all. `native.ts` fixes this with
`.replace("app.asar", "app.asar.unpacked")` on the computed path — a no-op in dev (no `app.asar`
substring exists on a plain filesystem path) and correct once packaged. Verified by launching the
actual packaged `.app` (not just `npm run dev`) with `--remote-debugging-port` and calling
`window.api.ping(...)` against it directly — this is the check that would have caught the bug if the
fix hadn't already been applied, and the reason to always re-verify from `dist/` after any change
near `native.ts`, `electron.vite.config.ts`'s main `external` rule, or `electron-builder.yml`'s
`files`/`asarUnpack`.
